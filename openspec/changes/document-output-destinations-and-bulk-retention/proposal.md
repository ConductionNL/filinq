# Proposal: document-output-destinations-and-bulk-retention

## Why

`DocumentService::generateDocument()` (verified at HEAD) always returns
generated bytes to the HTTP response — there is no way to land the output
in the requesting user's Nextcloud Files. Every generated beschikking,
brief, or report has to be downloaded by the caller and re-uploaded by hand
if it needs to live anywhere durable. Worse, `DocumentService::generateBulk()`'s
async path (`BatchDocumentJob`, >10 objects) generates every document and
then **discards the bytes** — `processObjects()` only ever records
`{objectId, status, warnings}` per item; the rendered content is never
persisted anywhere. For a 150-citizen-letter batch, 150 documents are
generated, held in memory one at a time, and thrown away. The job status
gives the caller a completion count and nothing to download.

Both gaps share one fix: a small, single-responsibility storage service
that lands generated bytes in `IRootFolder::getUserFolder()`, wired into
both the single-generate path and the batch job.

Priority **must-have** — the async bulk path is currently unusable for its
stated purpose (bulk *document generation*, not bulk document generation
*and deletion*).

## What Changes

- **`options.output` on `POST /apps/docudesk/api/documents/generate`**:
  `{mode: 'return' | 'files' | 'both', targetPath?: string}`. `mode`
  defaults to `'return'`, which is byte-for-byte today's behaviour (hard
  backward-compatibility requirement — see design.md D1).
  - `files`: store the generated binary via the new
    `DocumentStorageService` into the requesting user's Files
    (`IRootFolder::getUserFolder($userId)`); respond with JSON
    `{fileId, path, name, size, format}` instead of a binary download.
  - `both`: store AND return the binary download; the stored file's id/path
    are exposed via `X-Docudesk-File-Id` / `X-Docudesk-File-Path` response
    headers.
  - Default `targetPath`: `DocuDesk/<template namespace>/`, created
    recursively and idempotently. Filename collisions are resolved via
    `Folder::getNonExistingName()` — the same platform helper Nextcloud's
    own file list uses for its `name (2).ext` convention (D2).
- **New service**: `lib/Service/DocumentStorageService.php` — validates
  `targetPath` (relative, no `..`, no leading `/`, restricted charset),
  resolves/creates the destination folder, dedupes the filename, and
  writes the file. Nothing else. Unit-testable with `IRootFolder` mocks
  alone (D3).
- **Fail-open-for-`both`** (D4): a storage-layer failure (quota,
  permissions — anything thrown while writing to Files, after `targetPath`
  validation already passed) does NOT fail a `mode: 'both'` request —
  generation still succeeds and the binary is still returned, with a
  `warnings` entry describing the storage failure. `targetPath` validation
  failures (malformed input) are a hard 400 in every mode, including
  `both` — that is a caller mistake, not a transient storage condition, so
  it is not eligible for fail-open.
- **Audit trail**: `generatedDocument` (`DocumentService::logGeneratedDocument()`)
  gains two additive, nullable fields — `fileId`, `filePath` — populated
  whenever the document was actually stored. `docudesk_register.json`'s
  `generatedDocument` schema gains matching optional properties
  (`hardValidation: false`, so this is non-breaking for existing rows).
- **Async bulk requires `output.mode: 'files'`** (D5): a
  `generate/bulk` request for >10 objects that does not set
  `options.output.mode` to `'files'` is now rejected with HTTP 400 and an
  actionable message — generation is refused, not silently discarded as
  today. `'both'` is also rejected for the async path: there is no HTTP
  response to attach a binary download to once the job is queued, so
  offering it would silently behave like `'files'` while implying
  behaviour it can't deliver.
- **`BatchDocumentJob` stores each object's output** to Files, as the
  job's initiating user (userId captured at `dispatchBulkJob()` time — it
  is already threaded through `options['userId']` today for the job-status
  authorization check, so no new capture mechanism is needed), via the same
  `DocumentStorageService`. Per-job folder convention:
  `<targetPath>/<jobId>/` (D6), so a 200-document run doesn't spray 200
  files into one shared folder. Each job-status result item gains
  `{fileId, path}`; `GET /api/documents/jobs/{jobId}` returns them as part
  of the existing `results` array — no response-shape change needed.
- **Sync bulk (≤10 objects) honours `output.mode` per object**: `return`
  keeps today's inline `content`; `files` stores each object's output and
  returns `{fileId, path, name, size}` inline instead of `content`; `both`
  returns both. Reuses the single-generate default-`targetPath` convention
  (`DocuDesk/<namespace>/`) per object — not the per-job subfolder
  convention, which only applies to the async path.
- **Correspondence is explicitly out of scope** (D7): `CorrespondenceService`
  is a fully independent implementation of the same generate/bulk pattern —
  it does not call or share any code with `DocumentService`. Wiring
  `options.output` into it would mean re-implementing this entire change a
  second time against a different service, which is not "sharing
  `DocumentService` plumbing cheaply." Descoped; tracked as a follow-up
  idea, not a task, in design.md.
- **`document-generation-list-refs`' bulk note is unaffected**: that
  change's `REQ-DDLR-004` says `listRefs` is not wired into
  `generateBulk()` because the async job had no per-object output artifact
  to attach a resolved list to. This change gives the async job a
  per-object output artifact (a stored file), but wiring `listRefs`
  through bulk is still out of scope here — noted as a possible future
  follow-up, not attempted (would require re-litigating `listRefs`'
  guardrails in a job context; no user-facing need identified).

## Impact

- Affected specs: `document-creatie-sjablonen` (extends REQ-DCS-03 output
  format support and REQ-DCS-05 bulk document generation; all ADDs, no
  existing requirement is modified).
- Affected code:
  - `lib/Service/DocumentStorageService.php` (new)
  - `lib/Service/DocumentService.php` (`generateDocument()`,
    `generateBulk()`, `generateBulkSync()`, `dispatchBulkJob()`,
    `logGeneratedDocument()` — new `DocumentStorageService` constructor
    dependency)
  - `lib/BackgroundJob/BatchDocumentJob.php` (`processObjects()` stores
    each result and records `fileId`/`path`)
  - `lib/Controller/DocumentController.php` (`buildDocumentResponse()`
    branches on `output.mode`; `parseGenerateParams()` threads `filename`
    into `options` so the service layer can compute a storage filename
    without a new parameter)
  - `lib/Settings/docudesk_register.json` (`generatedDocument` schema:
    additive `fileId`/`filePath` properties; register/schema version bumps)
  - Tests: `tests/unit/Service/DocumentStorageServiceTest.php` (new),
    `tests/unit/Service/DocumentServiceTest.php`,
    `tests/unit/Controller/DocumentControllerTest.php`,
    `tests/unit/BackgroundJob/BatchDocumentJobTest.php` (all extended)
- No new routes — the existing `generate`/`generate/bulk` routes gain an
  optional request field (`options.output`).
