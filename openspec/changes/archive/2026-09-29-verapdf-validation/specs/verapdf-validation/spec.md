# verapdf-validation Specification (delta)

---
status: proposed
---

## Purpose

Integrate veraPDF — the reference ISO 19005 (PDF/A) validator — as an
optional, admin-installed local backend, replacing hope with verdicts: real
PDF/A-1b/2b/3b conformance validation, font-embedding verification with
remediation guidance, and a persisted per-document conformance report. The
integration follows the shipped optional-binary pattern (soffice,
Tesseract): probed availability, honest degradation, processing that never
leaves the instance.

## ADDED Requirements

### Requirement: veraPDF is an optional, probed, local validator backend (REQ-DDVPV-001)

The app MUST integrate veraPDF as a local CLI binary configured by app
config (`filinq.verapdf.binary_path` default `verapdf`,
`filinq.verapdf.max_seconds` default 60, `filinq.verapdf.enabled`), with
availability and version probed at use and displayed on the Filinq admin
settings page alongside the existing soffice/Tesseract status rows. The
binary MUST NOT be bundled with the app, document bytes MUST NOT leave the
instance, and an absent/disabled validator MUST degrade every consumer
honestly (heuristic-only mode with an explicit unavailable state) — never
error the base flows and never fabricate a verdict.

#### Scenario: Admin sees validator status

- GIVEN veraPDF installed on the server at the configured path
- WHEN the admin opens Filinq admin settings
- THEN the validator row shows available with the probed veraPDF version
- @e2e tests/e2e/spec-coverage/verapdf-validation.spec.ts

#### Scenario: Absent binary degrades honestly

- GIVEN no veraPDF binary on the instance
- WHEN any conformance validation is requested
- THEN the response states the validator is unavailable
- AND no verdict, report, or `compliant` value is fabricated
- @e2e exclude probe/degradation branch — covered by PHPUnit (tests/unit/Service/VeraPdfServiceTest.php)

### Requirement: Conformance validation validates the claimed flavour and returns rule-level results (REQ-DDVPV-002)

`VeraPdfService::validate()` MUST validate a PDF against the PDF/A flavour
the document itself claims in its `pdfaid` XMP identification (validate what
you claim), falling back to a requested or default profile (`3b`) when the
document claims nothing, and MUST return a machine-readable result:
`flavour`, `compliant`, `failedRules` (rule id, specification, clause,
failed-check count — references only, never document content),
`validatorVersion`. Validator timeout, crash, or unparseable output MUST
raise a typed error; a validator error MUST NEVER be recorded or reported
as compliant.

#### Scenario: Marker-claiming file fails real validation

- GIVEN a PDF whose XMP claims `pdfaid:part 3` / conformance B but violates ISO 19005-3 rules
- WHEN conformance validation runs
- THEN the result is `compliant: false` for flavour `3b` with the failed rules listed by clause reference
- @e2e exclude CLI invocation + parsing against fixture PDFs — covered by PHPUnit (tests/unit/Service/VeraPdfServiceTest.php)

#### Scenario: Validator failure is an error, not a pass

- GIVEN a veraPDF run that exceeds the configured time budget
- WHEN validation is attempted
- THEN a typed validator error is raised
- AND nothing records the document as compliant
- @e2e exclude timeout branch — covered by PHPUnit (tests/unit/Service/VeraPdfServiceTest.php)

### Requirement: Font embedding is verified and remediation guidance is attached (REQ-DDVPV-003)

Conformance results MUST report non-embedded fonts by font name (the CB
#182 e-depot trap: `convertExistingPdf()` imports pages as opaque XObjects
and cannot retroactively embed fonts), and the app MUST attach remediation
guidance derived from the failure shape: documents produced by Filinq's
own rendering paths (`convertHtml()`, the LibreOffice cascade) advise
regeneration through Filinq; imported or uploaded PDFs advise
re-conversion from the original source file and state the retroactive
limitation honestly. Guidance MUST be shown with the report and the
corresponding findings; the app MUST NOT claim it can repair fonts in
imported pages.

#### Scenario: Imported PDF failing on fonts gets the honest guidance

- GIVEN an uploaded PDF wrapped by `convertExistingPdf()` whose source never embedded Arial
- WHEN conformance validation runs
- THEN the report lists `Arial` under fonts not embedded
- AND the guidance states Filinq cannot embed fonts retroactively in imported pages and advises re-converting from the source document
- @e2e tests/e2e/spec-coverage/verapdf-validation.spec.ts

#### Scenario: Filinq-rendered artifact advises regeneration

- GIVEN a font failure on a document generated by Filinq's own rendering path
- WHEN the report renders
- THEN the guidance advises regenerating the document through Filinq
- @e2e exclude guidance-classification branch — covered by PHPUnit (tests/unit/Service/VeraPdfServiceTest.php)

### Requirement: A conformance report is persisted on the document and re-runnable (REQ-DDVPV-004)

`POST /api/validation/conformance/{fileId}` MUST run conformance validation
for a file resolved through the requesting user's folder (404 when not
resolvable, without existence disclosure) and persist the result as a
`conformanceReport` object via OpenRegister, keyed by `fileId` (re-running
updates the object): `flavour`, `compliant`, `failedRuleCount`,
`failedRules` (bounded reference list), `fontsNotEmbedded`,
`validatorVersion`, `validatedAt`, `trigger` (`manual` | `validation` |
`conversion`). The report MUST contain rule references and font names only
— no document content or personal data (AVG Art. 5(1)(c)); it is archival
evidence for e-depot hand-off. The document detail view MUST surface the
report (flavour, verdict, fonts, guidance).

#### Scenario: Conformance report is stored and shown

- GIVEN a readable PDF and an available validator
- WHEN the user runs the conformance check from the document detail view
- THEN a `conformanceReport` exists for the file with verdict, flavour and validator version
- AND the detail view shows the verdict with any failed rules and font findings
- @e2e tests/e2e/spec-coverage/verapdf-validation.spec.ts

#### Scenario: Re-running updates the same report

- GIVEN an existing `conformanceReport` for a file
- WHEN conformance validation runs again after the file was regenerated
- THEN the same report object is updated with the new verdict and `validatedAt`
- AND no duplicate report objects accumulate
- @e2e exclude idempotency-key persistence — covered by PHPUnit (tests/unit/Service/VeraPdfServiceTest.php)

#### Scenario: Inaccessible file yields 404

- GIVEN a fileId that does not resolve within the requesting user's folder
- WHEN the conformance endpoint is called
- THEN the response is HTTP 404 with a generic body
- @e2e exclude IDOR-safe resolution — covered by PHPUnit controller tests mirroring the ValidationController pattern
